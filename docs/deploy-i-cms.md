# Публикуване — Astro + Sveltia CMS върху споделен cPanel

Решение: статичен сайт с админ панел в браузъра. Разходи: **нула**.

---

## Проблемът, който трябваше да се реши

Sveltia CMS не записва на твоя хостинг. Тя записва **Markdown файл в GitHub**.
Само по себе си това не променя нищо на живия сайт — HTML файловете в
`public_html` си остават старите.

При хостинг като Cloudflare Pages това не е проблем: commit-ът автоматично
задейства ново билдване. При споделен cPanel няма кой да го направи.

**Липсващото звено е GitHub Actions** — той билдва и качва по FTPS сам.

## Веригата

```
   Пишеш в admin панела в браузъра
              ↓
   Sveltia прави commit в GitHub
              ↓
   GitHub Actions билдва Astro           ← безплатно
              ↓
   FTPS качва dist/ в public_html        ← безплатно
              ↓
   Сайтът е обновен (~1–2 минути)
```

---

## Частите и цената им

| Част | Услуга | Цена |
|---|---|---|
| Хранилище | GitHub (вече го имаме) | 0 |
| Билдване и качване | GitHub Actions — 2 000 мин./мес. за частни репота, неограничено за публични | 0 |
| Вход в админа | GitHub OAuth App | 0 |
| OAuth посредник | Sveltia CMS Authenticator на Cloudflare Workers | 0 (безплатен план) |
| Хостинг | твоят cPanel | вече платен |

Един билд на Astro отнема около минута, тоест 2 000 минути стигат за ~1 000
публикации месечно. Няма как да ги изчерпим.

---

## Защо е нужен OAuth посредник

Въпросът изниква логично: защо просто не се влиза с парола?

OAuth 2.0 изисква **client secret**, за да размени кода за токен. Sveltia работи
изцяло в браузъра, а client secret не може да стои в браузърен код — всеки може
да го види в кода на страницата. Затова размяната се прави от малък сървърен
скрипт. Sveltia предоставя свой готов — **Sveltia CMS Authenticator** — който се
качва на Cloudflare Workers за няколко минути.

Има и вариант без никаква настройка (резервният OAuth на Netlify), но той ни
прави зависими от чужда услуга без договор. За сайт, който ще монетизираме,
собственият worker е по-правилен.

## Работният файл на GitHub Actions

`.github/workflows/deploy.yml`:

```yaml
name: Build and deploy

on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: npm run build

      - name: Качване по FTPS
        uses: SamKirkland/FTP-Deploy-Action@v4.3.4
        with:
          server: ${{ secrets.FTP_SERVER }}
          username: ${{ secrets.FTP_USERNAME }}
          password: ${{ secrets.FTP_PASSWORD }}
          protocol: ftps
          local-dir: ./dist/
          server-dir: ./public_html/
```

Действието качва **само променените файлове**, а не целия сайт всеки път.

---

## Три места, където това се обърква

1. **`server-dir` е грешна.** Най-честата грешка. Билдът минава зелен, но сайтът
   не се променя, защото файловете са отишли в друга папка. При някои хостинги
   пътят е `./public_html/`, при други просто `./`. Проверява се веднъж с реален
   FTP клиент.
2. **Обикновен FTP вместо FTPS.** Паролата и съдържанието пътуват в чист текст.
   `protocol: ftps` не е по избор.
3. **Паролата в кода.** Данните за FTP влизат само в GitHub Secrets
   (Settings → Secrets and variables → Actions), никога във файл в репото.

---

## Компромисът, който приемаме

Публикуването не е мигновено — минава през билд и качване, тоест **1–2 минути**
от натискането на „публикувай“ до живия сайт. WordPress е мигновен.

За спортен сайт това е приемливо: дори при извънредна новина две минути не
решават нищо, а насреща получаваме нула поддръжка, нула риск от хакване и
отлични Core Web Vitals.

---

## Ред на изпълнение

1. Astro проектът със структурата на съдържанието *(следва след Стъпка 3)*
2. `.github/workflows/deploy.yml` + FTP данните в GitHub Secrets
3. Първо качване и проверка, че `server-dir` е правилната папка
4. `.htaccess` за HTTPS, каноничен домейн и компресия
5. Sveltia CMS + OAuth worker — добавя се последно, върху работещ сайт
