# Техническо решение — WordPress, статичен сайт или React

Въпросът е зададен като „кое е най-добро за оптимизация“. Отговорът има две части:
едната разбива често повтарян мит, другата е реален технически разделител, който
повечето сравнения пропускат.

---

## Част 1: Митът — „статичният сайт се класира по-добре“

Не е вярно в този вид. Google **не класира по технология.**

Core Web Vitals са потвърден фактор, но действат като **tiebreaker** — решават
между страници със сходно съдържание и авторитет, а не движат класирането сами
по себе си. Бърз сайт с плитко съдържание не изпреварва бавен сайт с
авторитетно съдържание. Значението им расте едва когато всичко останало е равно.

Практическият извод: WordPress може да е №1 в Google. Милиони новинарски сайтове
на WordPress се класират отлично. Скоростта е предимство, но не е това, което
печели.

**Ако това беше целият анализ, WordPress щеше да е очевидният избор.** Не е.

---

## Част 2: Реалният разделител — кой изобщо вижда страницата ти

Googlebot изпълнява JavaScript, но го прави на **две вълни**: първо чете суровия
HTML, после праща страницата в опашка за рендериране. Забавянето е от минути до
дни, а при сайтове с нисък приоритет — над седмица. За новинарски сайт, чиято
стойност е свежестта, това само по себе си е проблем.

Но същественото е другаде. **AI краулърите изобщо не изпълняват JavaScript.**

| Краулър | Изпълнява ли JS |
|---|---|
| Googlebot | ✅ Да (със забавяне) |
| GPTBot (ChatGPT) | ❌ Не |
| ClaudeBot | ❌ Не |
| PerplexityBot | ❌ Не |
| Facebook / X скрейпъри | ❌ Не |

Данните не са спекулация. Анализът на Vercel върху реален краулър трафик
установява, че никой от големите AI краулъри не рендерира JavaScript: GPTBot
изтегля JS файлове в ~11.5% от заявките, но не ги изпълнява; ClaudeBot ги
изтегля в ~23.84% и **никога** не ги изпълнява. Анализ на над 500 милиона GPTBot
заявки не намира нито едно доказателство за изпълнен JavaScript. Изследване на
Onely от февруари 2026 г. оценява, че **42% от JS-рендерираното съдържание
никога не влиза в AI системите.**

За спортна медия през 2026 г. това е решаващо. Все по-голяма част от търсенето
минава през AI отговори, а класически React SPA е **празна страница** за всичко
освен Googlebot.

### Оттук следва истинското разделение

Не е „WordPress срещу React срещу статичен“. То е:

| | Технологии | Видимост |
|---|---|---|
| ✅ **HTML идва готов от сървъра** | WordPress, статичен (Astro/Hugo), Next.js SSR/SSG | Всички краулъри виждат съдържанието веднага |
| ❌ **HTML се сглобява в браузъра** | Чист React (Vite/CRA), Vue SPA | Само Googlebot, със забавяне |

**Чистият React SPA отпада категорично** — не защото е бавен, а защото е невидим.
Ако искаш React, единственият приемлив вариант е Next.js със SSR или SSG.

---

## Част 3: Сравнение на трите реални кандидата

| | WordPress | Astro (статичен) | Next.js |
|---|---|---|---|
| HTML за всички краулъри | ✅ | ✅ | ✅ (в SSG/SSR режим) |
| Изисква от хостинга | PHP + MySQL | нищо — само файлове | Node.js |
| Публикуване без код | ✅ вграден админ | чрез Git или безплатна CMS | чрез Git или CMS |
| Core Web Vitals | средни, изискват работа | отлични по подразбиране | добри |
| Генериране на страници от JSON | болезнено (ACF, custom types) | 10 реда код | лесно |
| Поддръжка | update-и, плъгини, кеш | практически нула | средна |
| Риск от хакване | реален — WP е мишена №1 | няма какво да се хакне | нисък |
| Контрол над Schema.org | през плъгин | пълен, ръчен | пълен, ръчен |

## Препоръка за този конкретен проект: **Astro**

Не заради общи приказки за скорост, а заради три неща, специфични за нас:

**1. Стъпка 4 е точно това, в което Astro е силен.** Искаме таблици на
световните, европейските и клубните шампиони по години за всеки спорт. Това е
генериране на много страници от структурирани данни. В Astro е `getStaticPaths`
върху JSON файла — десетина реда, и всички страници съществуват. В WordPress
същото изисква custom post types, ACF полета и ръчно въвеждане на стотици записи
през админ панел. Часове работа срещу минути, и по-крехко.

**2. Хостингът ти вече го има — статичните файлове работят навсякъде.** Не
изискват PHP, MySQL, Node.js или версия на нещо. Качват се по FTP или rsync и
работят на всеки хостинг, включително най-евтиния план.

**3. Нула поддръжка и нула повърхност за атака.** Спортните сайтове на WordPress
са постоянна мишена — един непобновен плъгин и сайтът раздава спам линкове,
което убива класирането по-сигурно от всяка бавна страница.

### Възражението „но аз искам админ панел“

Решава се безплатно. **Decap CMS** или **Sveltia CMS** дават админ панел в
браузъра — заглавие, текст, снимка, бутон „публикувай“ — точно като WordPress,
но записват Markdown файл в Git вместо в база данни. Нула разходи, нула сървър.

### Кога WordPress би бил по-правилен

Ако утре екипът стане 4–5 автора, които не пипат код и публикуват по 20 материала
на ден, редакционният работен процес на WordPress (роли, чернови, планиране,
редакторски преглед) е по-зрял. При един до двама автори това предимство не се
усеща, а цената му — поддръжка и риск — се плаща всеки месец.

---

## Какво отпада окончателно

- ❌ **Чист React SPA** — невидим за AI краулърите и за социалните скрейпъри.
- ❌ **Всяка платформа, която сглобява съдържанието в браузъра.**

---

## Взето решение

**Astro, статично генериран, качван като готови файлове на споделения cPanel хостинг.**

Контекстът, който го потвърждава:

| Обстоятелство | Следствие |
|---|---|
| Споделен cPanel (PHP + MySQL) | Node.js не е надежден там → **Next.js отпада**. Статичните файлове работят винаги. |
| Публикуване през Claude | Работи веднага; **Sveltia CMS се добавя** върху това за писане от браузъра. |
| Хостингът е вече платен | Cloudflare Pages не е задължителен, но остава безплатен резервен вариант. |

### Как ще изглежда работният процес

```
Markdown файл в репото
        ↓  npm run build   (тук, в сесията)
   готови HTML файлове в dist/
        ↓  FTP / File Manager
   public_html на хостинга ти
```

Сървърът обслужва само статични файлове — няма PHP, няма база данни, няма
администрация и няма какво да бъде хакнато.

**Добавяме и Sveltia CMS** за писане направо от браузъра. Понеже тя записва в
Git, а не на хостинга, веригата се затваря от GitHub Actions, който билдва и
качва по FTPS. Пълната настройка: [deploy-i-cms.md](deploy-i-cms.md).

### Какво остава на хостинга да свърши

Един `.htaccess` файл за: пренасочване към HTTPS, каноничен домейн (със или без
`www`), gzip/brotli компресия и дълъг кеш за статичните ресурси. Това е цялата
сървърна конфигурация.
